# `aifaq_to_deploy` 旧项目资产审计与迁移说明

更新日期：2026年8月10日

原项目位置：`E:\big\aifaq_to_deploy`

定位说明：旧项目只作为历史实现与实验设计参考，不限制新项目采用更新的分块、检索、重排、生成或评价方法。

## 一、处理结论

旧项目不整体并入当前项目，也不修改、删除或移动。它保留为量子物理FAQ实验的历史证据和实现参考。当前项目只抽取以下可复用思想和干净代码：

1. 无上下文、噪声上下文、RAG、黄金上下文的分层实验设计；
2. JSONL形式的问题、答案、模型回答和逐题结果记录；
3. BM25与向量检索融合、知识库元数据隔离和引用返回的接口思想；
4. 独立的评测目录与客观指标脚本结构；
5. 新增到当前项目的严格JSONL读写和检索评价指标。

旧服务端、旧索引、模型权重、日志和历史实验输出均不复制，避免把凭据、量子物理数据、旧依赖和不可追踪状态带入CNC实验。

## 三、核心文件判断

### 3.1 `faq_server.py`

可借鉴：

- `/query`、上传、进度、文档列表和删除的服务边界；
- 非流式与流式回答；
- 回答中返回来源片段、相似度、文档ID和文件名；
- 语音网关和检索服务分开的思路。

不直接复用：

- Flask服务与`multiprocessing.managers.BaseManager`强耦合；
- 查询、文件上传、文档状态和远程Qdrant集中在单文件中；
- 使用pickle保存文档状态；
- 请求和完整回答写入日志，可能泄露用户内容；
- 开放CORS，缺少清晰的认证、输入大小限制和统一错误模式；
- 返回引用没有稳定的页码、章节、版本和知识类别字段。

迁移方式：当前CNC-RAG服务重新设计OpenAI兼容问答接口，并保留独立调试接口返回每路召回、融合、重排及引用信息。

### 3.2 `index_server.py` 与 `qdrant_custom.py`

可借鉴：

- `SentenceSplitter`与语义分块的可替换结构；
- Qdrant向量存储；
- BM25与向量检索并行召回；
- RRF融合；
- `agent_id`元数据过滤；
- 批量插入、进度跟踪和索引持久化。

不能原样复用的原因：

- 代码和配置中存在硬编码的远程服务地址及凭据；
- 使用旧版LlamaIndex接口，依赖版本锁定且迁移成本高；
- 文档页面先拼接为大文本，容易丢失页级元数据；
- 超过50万字符时直接截断，会静默丢失后半部分文档；
- 大文档某批次写入失败后可能跳过该批次，最后仍将进度写为100%；
- BM25中文分词依赖`nltk`中文停用词，运行环境不一定具备；
- 融合权重、Top-k和分块参数硬编码，缺少统一实验配置；
- 没有独立Cross-Encoder重排和标准检索指标。

迁移方式：保留“BM25 + 向量 + RRF + 元数据”的方法路线，在新服务中按独立模块重写，并为每一步保留可评测输出。

### 3.3 `mock.py`

可借鉴其上传、查询、进度和删除请求样例，但不直接复制。旧实现没有统一超时、重试和异常对象，部分函数打开文件后没有显式关闭；新项目应采用测试客户端或带超时的独立API客户端。

### 3.4 `eval_faq/`

真正值得保留的是实验结构，而不是所有旧脚本：

| 旧场景 | 代码中的真实含义 | CNC项目映射 |
|---|---|---|
| AF1 | LLM直接回答，无上下文 | `G0_no_context` |
| AF2 | 人工构造的带噪声长上下文 | `G1_noisy_context`，用于生成抗噪分析 |
| AF3 | 旧项目完整RAG系统 | 拆成BM25、向量、混合、元数据、重排等明确配置 |
| AF4 | 数据集中的干净参考文档 | `G_oracle_context`，作为生成上界 |
| AF5 | 使用AF3返回的相同检索片段，再用简单Prompt生成 | 不作为独立检索基线；只能测试上下文组织/Prompt差异 |

两份旧说明文档对AF3、AF4和AF5的命名存在冲突。迁移后不再使用AF编号，改用含义明确的场景ID。

## 四、旧实验数据质量核查

`eval/PhysicBench.json`实际是JSONL而不是单个JSON数组，共1282条，字段为`id`、`doc`、`question`和`answer`。

部分旧结果不完整：

- `eval/af1.dqas.json`：1279条；
- `eval/af2.dqas.json`：1278条；
- `eval/af3.dqas.json`：1103条；
- `eval/af4.dqas.json`：1282条；
- 多个教师模型评分目录也存在缺行；
- 说明文档有时写1283条，实际主文件为1282条。

因此旧论文表格或平均分不能直接迁入新论文。若引用旧项目经验，必须重新核对参与平均值计算的样本集合。

## 五、旧评测方法的可用性

### 可以复用

- 逐题保存问题、参考答案、模型回答和评分；
- 无上下文与黄金上下文形成性能下界/上界；
- 使用多个评价者减少单一LLM裁判偏差的思路；
- BLEU、ROUGE和BERTScore作为补充指标的代码组织方式；
- 单条失败不应中断整个批量实验的工程处理。

### 必须修改

1. 旧LLM裁判只有一个0～10分总分，需要拆成正确性、忠实性、完整性、引用准确性和拒答准确性；
2. 不能把解析失败默认记为0后直接纳入平均，应记录为评价失败并单独统计；
3. 结果文件末尾追加`Average score:`会破坏JSONL格式，汇总信息必须单独保存；
4. BLEU/ROUGE对开放式中文技术回答只能作为辅助，不能作为主要结论；
5. BERTScore需要记录逐题结果、明确模型版本和离线缓存；
6. 旧项目没有Recall@k、MRR和nDCG等检索指标，新项目已补充；
7. AF5使用与AF3相同的检索结果，不能证明“传统检索器”和“优化检索器”的差异；
8. 需要固定相同问题集合，缺失样本不能由不同方法各自忽略后直接比较平均分。

## 六、安全与环境风险

旧项目多个Python文件含看起来仍可用的API/Qdrant凭据。它们没有复制到新项目，也没有写入本审计文件。建议在相应服务后台立即轮换或吊销，并检查Git历史；仅从当前工作区删除字符串不能消除Git历史中的泄露。

旧项目Git工作区存在大量已修改、已删除和未跟踪文件，本次审计没有修改它们。不要在该目录执行清理、重置或批量删除。

位置：`services/cnc-rag/evaluation/`

- `jsonl_io.py`：严格JSONL读写，兼容识别旧文件尾部平均分但默认拒绝；
- `retrieval_metrics.py`：Recall@k、Hit@k、MRR和nDCG@k；

这里只抽取通用评测资产，不复制量子物理语料、旧结果、旧索引和任何凭据。
