# RAG评估与来源标注规范

更新日期：2026年8月19日

## 为什么必须标来源

只有问题和标准答案，只能粗略评价最终回答像不像标准答案，无法判断：

1. 检索器有没有找到正确材料；
2. 模型回答是否忠实于检索证据；
3. 引用的页码和片段是否真的支持答案；
4. 回答错误来自检索、上下文组织还是生成模型。

因此每道可回答问题至少需要同时标注标准答案和支持答案的证据。无答案问题则需要明确标记不存在支持证据。

## 本项目的四层标识

| 层级 | 标识示例 | 作用 |
|---|---|---|
| 文档 | `DOC004` | 锁定来源手册及版本 |
| 原始OCR行 | `DOC004_P117_L011` | 回到页面坐标和OCR结果 |
| 结构块 | `DOC004_P117_B011` | 保存人工校正前后的结构单元 |
| 检索chunk | 后续如 `DOC004_C000123` | 作为检索器实际返回和评价的最小对象 |

`evidence_id`（如`EDEV013`）表示人工确认的一条语义证据。它可以跨越多个结构块或相邻页面。正式chunk生成并冻结后，每条证据还要映射到一个或多个`gold_chunk_id`。

## 当前文件关系

```text
questions.draft.jsonl
  question_id
      │
      ├── answers.reviewed.jsonl ── evidence_ids
      │                                │
      │                                └── reviewed_evidence.v0.1.jsonl
      │                                      ├── document_id
      │                                      ├── pdf_pages / printed_pages
      │                                      ├── source_block_ids
      │                                      └── reference_text
      │
      └── retrieval_eval.reviewed.jsonl ── relevant evidence + relevance grade
```

`answers.with_citations.jsonl`是自动联结后的便于查看版本，把上述来源字段直接展开到每条答案中。规范化文件仍以`answers.reviewed.jsonl`和`reviewed_evidence.v0.1.jsonl`为准，避免同一证据在多处手工修改而不一致。

## 正式chunk生成后的检索标注

每道问题的检索金标准应形如：

```json
{
  "question_id": "QDEV013",
  "relevant_chunks": [
    {"chunk_id": "DOC004_C000123", "relevance": 2, "evidence_id": "EDEV013"},
    {"chunk_id": "DOC004_C000124", "relevance": 1, "evidence_id": "EDEV013"}
  ]
}
```

相关性建议：2表示直接、充分支持答案；1表示部分支持或提供必要背景；0表示不相关。0级通常不必全部写入金标准，可在人工抽查候选结果时记录。

不同切块策略会产生不同chunk编号，因此相关性不能简单复制。应先用`source_block_ids`自动产生候选映射，再人工处理证据跨块、表格拆分和边界重叠。

## 三部分评价

### 1. 检索评价

- Recall@K：相关chunk有多少进入前K；
- Hit@K：前K是否至少命中一条相关chunk；
- MRR：第一条相关chunk出现得有多靠前；
- nDCG@K：考虑多级相关性后的排序质量。

### 2. 生成评价

- 答案正确性：与人工标准答案是否一致；
- 忠实性：回答中的事实是否能由实际检索上下文支持；
- 答案完整性：金标准要点是否覆盖；
- 引用精确率：引用的chunk是否真的支持对应陈述；
- 引用召回率：需要证据的关键陈述是否都有引用；
- 安全性：涉及碰撞、刀补、加工参数时是否保留必要条件和警示。

生成评价必须保存模型实际看到的`retrieved_chunk_ids`和完整回答，不能只保存一个总分。

### 3. 端到端评价

端到端结果要能够区分：检索未命中、命中但排序靠后、上下文命中但模型误答、答案正确但引用错误、知识库无答案却强行作答。无答案和歧义问题需要单独评价拒答及澄清能力。

## 数据泄漏边界

- `source_page_hint`只供标注者定位，禁止作为检索输入；
- 开发集可用于选参数，正式测试集不能参与调参；
- 问题由某段证据生成时，应在报告中说明，不能把同源小样本成绩当泛化性能；
- 语料、chunk、问题、标注和实验配置均需冻结版本与哈希。
