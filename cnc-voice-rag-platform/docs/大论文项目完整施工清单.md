# 面向数控加工现场的语音交互式RAG知识服务——完整施工清单

更新日期：2026年8月20日

暂定题目：**面向数控加工现场的语音交互式检索增强知识服务研究**

## 一、项目最终目标

完成一篇由“主要方法、应用改进、验证系统”组成的硕士论文：

1. 主要方法：面向数控技术文档的结构化切块、混合检索和型号/版本元数据约束；
2. 应用改进：面向CNC术语、G/M代码、参数号的语音识别后规范化；
3. 验证系统：ESP32语音终端接入ASR、RAG、LLM和TTS，验证现场免手输入的可行性。

本项目不做知识图谱，不从头训练大语言模型，不把ASR、TTS和ESP32接入本身包装成算法创新，也不控制真实机床。

## 二、必须遵守的工作规则

- 所有项目文件、模型、缓存、数据和临时文件均放在`E:\big`，不得放入C盘。
- 原始PDF、原始OCR JSON和原始页面图片只读保存，不直接覆盖。
- 人工修订必须通过修订表或新版本文件完成，并保留修改人、日期和原因。
- 任何答案都必须标注文档、章节、PDF页码和对应原文证据。
- 开发集可以用于调参数；最终测试集冻结后不得用于反复调参。
- 所有实验必须记录数据版本、切块配置、模型、参数、代码版本和结果文件。
- 文件名中的`draft`表示草稿，禁止直接改名冒充正式数据。
- 不根据常识擅自修改G/M代码、参数、数值、单位或安全操作内容。
- 协作者遇到看不清或无法确定的内容应标记`cannot_confirm`，不能猜测填写。

## 四、人员分工建议

### 4.1 数据整理与复核人员

负责：

- 对照PDF页面检查OCR文字；
- 检查标题层级、页码、代码、参数和表格；
- 填写修订结果和不确定项；
- 根据原文编写问题、参考答案和证据位置。

不得负责：

- 擅自修改切块脚本；
- 自动生成大量未经核验的问题；
- 根据网络资料补写书中不存在的答案；
- 直接修改已有chunk编号或gold编号。

### 4.2 RAG与实验人员

负责：

- 应用人工修订并重新生成结构块；
- 生成不同切块配置；
- 建立BM25和向量索引；
- 运行对比、消融和错误分析；
- 维护可追溯引用和实验配置。

### 4.3 语音与系统人员

负责：

- 采集CNC语音查询；
- 接入ASR和TTS；
- 建立术语、代码和混淆表达词表；
- 接入小智服务端和ESP32；
- 进行端到端功能与时延测试。

语音和硬件人员应在文本RAG稳定后开始正式联调。

## 五、第一阶段：马上执行的数据复核任务

### 5.1 输入文件

- 复核清单：`data/parsed/DOC004/data_review_queue_v0.2.csv`
- 页面图片：`data/parsed/DOC004/rendered/page_XXX.png`
- OCR来源块：`data/parsed/DOC004/blocks.batch_001.draft.jsonl`
- 已复核证据：`data/evaluation/dev_v0.1/reviewed_evidence.v0.1.jsonl`

第一批只处理CSV中`priority=P0`的42项，不先处理剩余P1项目。

### 5.2 每条记录的操作步骤

- [ ] 根据`page_image`打开对应原始页面。
- [ ] 在页面上定位`block_id`对应的`text`。
- [ ] 检查文字是否完整、顺序是否正确。
- [ ] 重点检查数字0与字母O、数字1与字母I、G00/G01、负号、小数点和下划线。
- [ ] 检查G/M代码、参数格式、单位、正负值和括号。
- [ ] 检查`title_path`是否属于正确章节。
- [ ] 表格内容应按行理解，避免把多列内容错误拼成一句话。
- [ ] 在`corrected_text`填写最终确认文本；即使原文正确，也填写确认后的完整文本。
- [ ] 在`corrected_title_path`填写最终章节路径，格式为`第X章 > X.X节 > X.X.X小节`。
- [ ] 能确认时将`review_status`改为`reviewed`。
- [ ] 无法确认时将`review_status`改为`cannot_confirm`并填写原因。
- [ ] 在`review_note`记录修订内容，例如“GOO改为G00”“表格按四行恢复”“原文无误”。

### 5.3 复核时禁止的操作

- 不修改`block_id`、`pdf_page`、`evidence_ids`和`short_chunk_ids`。
- 不直接编辑原始OCR JSON、原始图片或已有chunk文件。
- 不把网上查到的相似说明当作当前手册原文。
- 不因OCR置信度低就默认文字错误，必须查看页面。
- 不将图中的尺寸标注、程序代码和正文随意合并。

### 5.4 第一批交付物

- [ ] 填写完成的`data_review_queue_v0.2.csv`副本；
- [ ] `review_status=reviewed`或`cannot_confirm`的42项均不得留空；
- [ ] 单独列出所有`cannot_confirm`项目；
- [ ] 填写复核人、复核日期和备注；
- [ ] 不改动其他项目文件。

### 5.5 第一批验收标准

- 42个P0项目全部处理；
- G/M代码、数值、单位和正负号均能在页面上找到依据；
- 标题路径与页码范围一致；
- 每一次修改都有备注；
- 不确定内容没有被猜测性修正。

## 六、第二阶段：形成干净的小型知识库

该阶段由RAG人员执行。

### 6.1 应用人工修订

- [ ] 将复核表转换为独立的block修订文件。
- [ ] 保留原始OCR块不变。
- [ ] 生成`blocks.reviewed_v0.1.jsonl`。
- [ ] 每个修订块保留原block编号、原文、修订后文字、修订人和日期。
- [ ] 重新运行来源块完整性校验。

### 6.2 重新生成切块

- [ ] 生成256 token固定切块，约20%重叠。
- [ ] 生成512 token固定切块，约20%重叠。
- [ ] 生成1024 token固定切块，约20%重叠。
- [ ] 生成最大512 token的结构化切块。
- [ ] 指令格式、参数解释、表格行和程序段尽量不从中间切开。
- [ ] 每个chunk保存来源块、章节、PDF页码、印刷页码和原文引用。
- [ ] 生成manifest和SHA256。

### 6.3 人工确认gold chunk

- [ ] 对每道问题逐一查看四种切块下的候选chunk。
- [ ] 标记相关性：2=完整相关，1=部分相关，0=不相关。
- [ ] 多证据问题应确认所有必要证据是否被覆盖。
- [ ] 删除仅因来源块局部相交而产生的假相关候选。
- [ ] 记录无法由当前知识库回答的问题。

### 6.4 第二阶段交付物

- 干净的来源块文件；
- 四套重新生成的chunk；
- 人工确认的gold chunk标签；
- 数据质量报告；
- 知识库版本号和哈希清单。

### 6.5 第二阶段验收标准

- 所有30道开发问题均能追溯到原始页面；
- chunk没有空文本、重复编号或无效来源；
- 引用原文、页码和来源块一致；
- 复核数据和自动生成数据状态明确区分；
- 同一命令可以重复生成完全一致的结果。

## 七、第三阶段：扩展正式语料与评测集

### 7.1 文档范围

优先围绕同一数控系统或同一设备系列扩展，避免一开始混入大量不同版本资料。

建议依次加入：

1. 编程与G/M指令；
2. 基础操作流程；
3. 参数说明；
4. 报警含义；
5. 维护与安全说明。

每份文档登记：文档ID、名称、厂商、设备型号、数控系统、版本、来源、类别、页数和文件SHA256。

### 7.2 文档处理

- [ ] 判断是可复制PDF还是扫描PDF。
- [ ] 执行文本解析或OCR。
- [ ] 删除页眉、页脚和重复页码。
- [ ] 恢复标题层级和连续章节。
- [ ] 单独处理表格、代码和图注。
- [ ] 抽样核验普通页面。
- [ ] 全量核验会进入评测答案的证据页面。

### 7.3 问题类型

问题集至少包含：

- 代码或术语解释；
- 指令格式和参数含义；
- 操作或维护步骤；
- 报警含义及辅助排查；
- 表格参数查询；
- 带型号或版本条件的查询；
- 跨段证据问题；
- 表述不同但语义相同的问题；
- 信息不足的歧义问题；
- 文档中不存在答案的问题；
- 涉及高风险操作的问题。

### 7.4 每道问题必须填写的字段

- question_id；
- question；
- question_type；
- difficulty；
- reference_answer；
- evidence_ids；
- document_id；
- PDF页码和印刷页码；
- 型号和版本条件；
- answerable；
- safety_level；
- annotation_status；
- reviewer。

### 7.5 数据规模

- 第一批正式闭环：3至5份文档、约100道问题；
- 后续论文正式数据：根据文档质量扩展到约300至500题；
- 优先保证证据正确，不为凑数量批量保留低质量自动问题。

### 7.6 数据集划分

- 开发集：用于选择切块、融合权重和阈值；
- 测试集：最终冻结，只用于正式报告结果；
- 问题不能仅通过改写同一个答案在开发集和测试集中重复出现；
- 同一程序实例或同一表格派生的问题尽量放在同一划分中，减少泄漏。

## 八、第四阶段：文本检索基线

先只评价能否找到正确证据，不接语音和硬件。

### 8.1 必做基线

- [ ] BM25；
- [ ] 通用中文/多语言向量检索；
- [ ] BM25与向量固定RRF融合；
- [ ] RRF融合加Cross-Encoder重排；
- [ ] 本文完整方法。

### 8.2 切块对照

- [ ] 256 token固定切块；
- [ ] 512 token固定切块；
- [ ] 1024 token固定切块；
- [ ] 结构化切块。

切块实验中保持语料、问题、检索器和Top-K一致，只改变切块配置。

### 8.3 检索指标

- Recall@1、Recall@3、Recall@5、Recall@10；
- Hit@K；
- MRR；
- nDCG@5或nDCG@10；
- 平均检索延迟；
- chunk数量、索引大小和构建时间。

### 8.4 分类分析

分别报告：

- 精确代码类；
- 自然语言描述类；
- 步骤类；
- 型号/版本类；
- 表格类；
- 多证据类；
- 无答案类。

### 8.5 验收标准

- 每组实验均可用固定命令重复运行；
- 检索结果保存Top-K chunk、分数和引用；
- 不能只报告一个总体分数；
- 至少完成失败案例分析；
- 不能用最终测试集选择最优参数。

## 九、第五阶段：论文核心RAG方法

### 9.1 结构增强

- 将章节路径加入检索文本；
- 保留父章节与叶子chunk关系；
- 代码、参数表和说明作为完整知识单元；
- 必要时采用“小块检索、大块返回”，避免检索粒度和生成上下文粒度完全绑定。

### 9.2 混合检索

- BM25负责G/M代码、参数号、报警号和精确术语；
- 向量检索负责口语表达、同义表达和描述性问题；
- 固定RRF作为普通混合基线；
- 根据查询中是否存在代码、参数和自然语言描述调整融合方式，作为候选完整方法。

### 9.3 元数据约束

- 显式型号或版本采用硬过滤；
- 推测条件采用软加权；
- 条件缺失且会影响答案时要求澄清；
- 不在冲突版本之间拼接答案。

### 9.4 重排与证据组织

- 对融合后的Top-N候选进行重排；
- 去除重复证据；
- 补充必要的父标题或相邻上下文；
- 控制最终送入LLM的证据数量和总token数。

### 9.5 主实验控制

主对比保持约5组：

1. BM25；
2. 向量检索；
3. 固定RRF；
4. 固定RRF加重排；
5. 结构增强、查询特征融合和元数据约束的完整方法。

关键消融约3项：

1. 去掉章节结构和父级上下文；
2. 去掉查询特征融合，退回固定RRF；
3. 去掉型号和版本约束。

## 十、第六阶段：回答生成与引用

### 10.1 生成规则

- LLM只能读取本次实际检索到的证据；
- 不得把gold答案或gold证据编号放入生成提示；
- 回答必须包含直接结论、适用条件、必要步骤、来源和安全提示；
- 证据不足时拒答；
- 版本冲突时分别说明或要求确认；
- 不用模型常识补写文档没有给出的参数。

### 10.2 回答评价

- 答案正确性；
- 答案忠实性；
- 答案完整性；
- 引用准确率；
- 引用覆盖率；
- 无答案拒答准确率；
- 版本冲突处理准确率；
- 安全提示触发准确率；
- 生成延迟。

自动评价必须配合人工抽样复核，不能只报告LLM打分。

## 十一、第七阶段：语音查询规范化

文本RAG稳定后再执行。

### 11.1 语音数据

- 采集约150至300条CNC语音查询；
- 包含字母、数字、中英文混合、G/M代码、参数号和报警号；
- 包含安静环境和至少一种可重复的工业噪声；
- 保存音频、说话人编号、标准转写、场景和噪声条件；
- 不在没有授权时公开说话人隐私信息。

### 11.2 基线

1. 干净文本查询；
2. ASR原始文本；
3. 通用LLM直接纠错；
4. CNC领域受约束规范化。

### 11.3 规范化方法

- 建立CNC术语、代码和参数词表；
- 建立拼音、读音、字母和数字混淆对；
- 从领域词表召回候选；
- 综合读音、字形、上下文和RAG证据排序；
- 保留原ASR文字和修改轨迹；
- 低置信度关键代码要求用户确认；
- 必须允许“不修改”。

### 11.4 评价指标

- CER/WER；
- 专业术语准确率；
- 代码完全匹配率；
- 过度纠错率；
- 规范化前后Recall@5；
- 规范化前后答案正确率。

## 十二、第八阶段：ESP32硬件验证平台

### 12.1 硬件边界

ESP32只负责：

- 麦克风采集；
- 按键说话；
- 音频上传；
- TTS音频接收与播放。

服务器负责ASR、规范化、检索、LLM和TTS。系统不得直接控制机床。

### 12.2 接入顺序

- [ ] 先用网页或命令行完成文本问答；
- [ ] 再用电脑麦克风完成ASR—RAG—TTS；
- [ ] 最后接入小智服务端和ESP32；
- [ ] 每次请求保存统一request_id；
- [ ] 能定位失败发生在音频、ASR、规范化、检索、生成还是TTS。

### 12.3 系统测试

- 代码解释；
- 操作步骤；
- 报警查询；
- 型号限定；
- 无答案问题；
- 版本冲突；
- “下一步、重复、停止、来源是什么”；
- 网络中断和服务异常；
- 端到端响应时间和任务完成率。

## 十三、第九阶段：论文写作对应关系

### 第1章 绪论

研究背景、研究现状、现有不足、研究内容、技术路线和论文结构。

### 第2章 相关理论与总体方案

数控文档特点、RAG、BM25、向量检索、混合检索、ASR/TTS和总体系统架构。

### 第3章 核心方法

数据构建、结构化切块、结构增强、混合召回、元数据约束、重排、引用，以及主实验和消融实验。

### 第4章 语音应用改进

CNC术语和代码的ASR错误、领域词表、受约束规范化、语音实验和错误分析。

### 第5章 系统实现与验证

需求、架构、ESP32和小智接入、模块实现、功能测试、性能测试和典型案例。

### 第6章 总结与展望

根据最终实验结果总结贡献、局限和后续工作，不提前虚构创新结论。
