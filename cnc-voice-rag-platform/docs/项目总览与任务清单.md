# 项目总览与任务清单

更新日期：2026年8月10日

## 一、现在已经确定的内容

### 研究对象

面向数控加工现场的技术知识服务，内容可覆盖操作、编程、参数、报警、维护和安全，但正式数据集优先限定到一个数控系统或一套设备资料。

### 研究主线

```text
数控技术文档
  → 结构解析、分块和型号/版本元数据
  → 可重复评价的文档索引

现场语音
  → VAD与ASR
  → CNC术语、代码和参数查询规范化
  → 候选检索方法对比
  → 证据充分性、冲突和风险检查
  → 带引用回答
  → TTS与ESP32输出
```

### 工作边界

- 不构建知识图谱；
- 不控制机床；
- 不研究振动、电流等传统故障信号；
- 不训练通用大模型；
- ASR/TTS和ESP32是语音链路与验证手段；
- 优先研究文本RAG，再加入语音，最后接硬件。

## 二、技术更新原则

旧量子物理FAQ项目和当前技术路线中的算法名称都不是最终绑定方案。真正需要长期保持稳定的是：

1. 文档、问题、证据和元数据的数据协议；
2. 文本输入、检索调试和OpenAI兼容问答接口；
3. Recall@k、MRR、nDCG、忠实性、引用、拒答和延迟等评价口径；
4. 基线、完整方法和消融实验使用同一数据与配置的公平比较规则；
5. 每次实验可追溯到数据、模型、参数和代码版本。

具体分块器、Embedding、向量库、融合算法、重排器、LLM和评价器都允许替换。替换条件是：

- 在相同测试集上与已有基线比较；
- 能说明提升来自哪个模块；
- 同时报告准确率、延迟和资源代价；
- 不因为“更新”而无限增加论文工作量；
- 新方法稳定后再写成论文研究点。

## 三、`E:\big` 下三个主要项目的关系

```text
E:\big\
├─ cnc-voice-rag-platform\   当前论文主项目，后续主要在这里工作
├─ xiaozhi-esp32-server\     小智完整源码，只作为上游参考
└─ aifaq_to_deploy\          旧量子物理FAQ，只作为历史参考
```

### 小智项目提供什么

- ESP32与服务端WebSocket/Opus通信；
- VAD、ASR和TTS调用链；
- 按键、打断及音频回传的工程底座。

它不负责论文的核心RAG算法。主项目目前只保留其后端副本 `vendor/xiaozhi-server/`，等语音链路跑通后再裁剪无关功能。

### 旧FAQ项目提供什么

- Flask问答和文档管理接口参考；
- BM25、向量和RRF融合的旧实现经验；
- 无上下文、噪声上下文、RAG和黄金上下文实验思路；
- JSONL结果与自动评价脚本参考。

它不会成为新项目的运行依赖。旧代码含凭据、旧依赖、量子物理索引和不完整实验，不能直接用于新论文。

## 四、主项目文件说明

### `docs/`

| 文件 | 作用 | 使用时机 |
|---|---|---|
| `项目总览与任务清单.md` | 当前统一入口 | 每次继续工作前 |
| `导师审阅稿_课题方案.md` | 给导师看的课题方案 | 现在 |
| `完整技术路线_审阅稿.md` | 完整数据链、算法链和实验链 | 导师审阅/技术设计 |
| `thesis-outline.md` | 七章论文目录 | 题目确认后 |
| `后续实施步骤.md` | 更细的阶段验收步骤 | 实施阶段 |
| `architecture-and-pruning.md` | 小智接入与裁剪边界 | 语音联调阶段 |
| `aifaq旧项目资产审计.md` | 旧FAQ项目复用及风险 | 设计实验时回查 |

### `data/`

建议形成：

```text
data/
├─ raw/           原始PDF，只读保存
├─ parsed/        按页解析的统一中间格式
├─ chunks/        带章节和页码的检索片段
├─ terminology/   CNC术语、代码、参数和ASR混淆词
├─ evaluation/    问题、标准答案和证据标注
└─ manifests/     文档来源、版本、哈希及许可
```

目前只有规范说明和空目录，没有正式数控文档和标注数据。

### `scripts/`

当前 `parse_documents.py` 是PDF按页及文本块解析原型，可以用于快速检查文档是否可提取，但还不具备标题层级恢复、表格识别、页眉页脚清理和扫描件OCR，不能直接作为正式数据流水线。

### `experiments/`

当前 `baselines/bm25_baseline.py` 只是BM25演示代码。正式实验需要读取真实chunks和固定测试集，并统一输出逐题排名、分数、耗时和汇总指标。

### `models/`

当前为空。只有确定需要本地模型后才放入，模型目录需要记录来源、版本、许可证和校验值。大型模型不重复复制。

### `services/cnc-rag/`

这是后续核心开发位置。计划模块包括解析、元数据、术语、索引、查询规范化、检索、融合、重排、证据判断、生成、API和评价。

目前已完成：

- 严格JSONL读写；
- Recall@k、Hit@k、MRR和nDCG@k；
- 新的检索、生成和语音实验场景定义；
- 评测模块单元测试。

尚未实现真正的文档索引、检索API和回答生成。

### `vendor/xiaozhi-server/`

这是第三方语音网关副本。短期保持上游结构，不在里面实现论文RAG，避免语音通信、模型调用和核心实验互相耦合。

## 五、现在唯一推荐的执行顺序

### 第0阶段：导师确认

- [ ] 审阅题目和两项方法研究点；
- [ ] 确认不做知识图谱；
- [ ] 确认ESP32只做验证平台；
- [ ] 确认是否限定一个数控系统或设备系列；
- [ ] 记录导师对数据规模、创新点和硬件的要求。

出口：形成一页“课题确认记录”，之后不随意扩大范围。

### 第1阶段：数据小闭环

- [ ] 选3～5份同一系统或设备系列的文档；
- [ ] 建立文档manifest，登记来源、型号、版本、哈希和许可；
- [ ] 用现有解析脚本检查PDF质量；
- [ ] 人工建立首批20～30个问题及证据页码；
- [ ] 完成第一版术语、G/M代码和参数词表；
- [ ] 明确chunk和evidence的唯一ID规则。

出口：每道问题能够追溯到原文页码，数据格式稳定。

### 第2阶段：正式文本基线

- [ ] 改造PDF解析，保留标题、页码、表格和代码条目；
- [ ] 完成固定长度、章节层级和语义分块；
- [ ] 跑通BM25与向量检索；
- [ ] 用统一评测模块输出Recall@k、MRR和nDCG；
- [ ] 保存逐题检索结果和失败类型。

出口：可以用一条命令重复构建索引和生成基线结果。

### 第3阶段：选择完整RAG方法

- [ ] 在基线结果上判断真正瓶颈；
- [ ] 再决定采用何种混合召回、融合、元数据策略和重排器；
- [ ] 对每个新增模块做单独消融；
- [ ] 实现引用、拒答、版本冲突和安全提示；
- [ ] 冻结主实验配置。

出口：完整方法相对基线有稳定、可解释的增益。若新方法更好，可以在此阶段替换旧方案。

### 第4阶段：语音查询规范化

- [ ] 固定一个ASR基线；
- [ ] 建立CNC术语、代码和噪声语音测试集；
- [ ] 比较标准文本、ASR原文、词表纠错和受约束纠错；
- [ ] 同时评价CER/WER、代码准确率和下游检索效果；
- [ ] 为低置信度关键代码增加复述确认。

出口：查询规范化不仅改善文本指标，也稳定改善检索或回答。

### 第5阶段：ESP32验证

- [ ] 先跑通电脑端音频链路；
- [ ] 再确认板卡、麦克风、功放/扬声器和按键；
- [ ] 接入小智语音网关；
- [ ] 测试提问、停止、重复和下一步；
- [ ] 记录端到端延迟、任务完成率和失败归因。

出口：稳定完成“语音提问—带依据回答—语音播报”闭环。

### 第6阶段：论文与归档

- [ ] 冻结数据、配置、代码和结果；
- [ ] 先写数据章节，再写方法、系统和实验章节；
- [ ] 图表与原始结果建立一一对应关系；
- [ ] 记录所有开源代码、模型和文档来源；
- [ ] 最后确定哪些研究点能够称为创新点。

## 六、当前不要做的事情

- 不因为旧FAQ中有现成代码就直接部署旧Qdrant和旧LlamaIndex；
- 不提前下载和比较大量模型；
- 不在没有固定数据集时选择“最终最佳算法”；
- 不先开发网页、管理后台或复杂硬件交互；
- 不微调ASR或Embedding，除非基线证明它们是主要瓶颈；
- 不把自动评价分数作为唯一结论；
- 不在小智源码内部直接堆叠论文核心RAG代码。

## 七、下一次开始工作的默认任务

如果导师尚未反馈：盘点可用数控文档，建立manifest和首批20～30个带证据问题。

如果导师已经确认：立即执行第1阶段数据小闭环，不先做硬件。
